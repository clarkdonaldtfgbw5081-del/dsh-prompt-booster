# 提示词工程说明

这页说明本插件如何组织系统提示词、任务上下文和输出契约。它不是给模型的另一个提示词，而是维护提示词时的设计约束。

## 原则

1. **最小核心**
   系统提示词只保留所有任务都需要的部分：改写者身份、输入边界、原意保护、输出结构和完成定义。页面方案、排错步骤、写作语气等任务知识不写进核心提示词。

2. **按需展开**
   `modelInput()` 只发送当前任务会用到的字段：
   - 写作、研究、分析通常只带 `task_intent` 和长度预算；
   - 软件任务才带 `solution_strategy`；
   - 页面与任务交付默认项只在 `default_choices` 非空时发送；
   - 没有逐字保护片段时不发送 `protected_fragments`；
   - `context_sources`、`preferences` 为空时不占模型上下文。

3. **任务指导就近**
   任务相关的指引放在产生它的模块里，而不是全部塞进 `SYSTEM_PROMPT`：
   - `intent.ts`：任务类型、交付阶段、已有项目等轻量判断；
   - `strategy.ts`：软件任务的方案边界与按能力选择的验证方向；
   - `defaults.ts` / `task-defaults.ts`：可调整的页面方案与任务交付默认项；
   - `guards/`：确定性约束检查；
   - `engine.ts`：修复请求和总预算。

4. **少写菜谱，多写目标和边界**
   当前模型对任务意图的理解已经足够强，过细的逐条步骤会压缩用户的真实要求，也容易让模型只记住模板。核心提示词使用正面目标（“保留原意、说明交付、遵守预算”），只有安全边界、输出契约和用户可见行为才写成硬规则。

5. **提示词不是安全边界**
   不执行任务、不自动发送、不增加用户没有要求的功能，这些由产品结构和本地守卫保证；提示词负责表达意图，`guards/` 负责兜底。修改提示词时不要假设模型一定会遵守所有文字，新增约束优先加到守卫和测试。

6. **先定义完成**
   完成定义写在核心提示词末尾：JSON 可解析、原要求与逐字约束完整、默认项不过界、正文在预算内。模型不需要输出自评，但需要知道什么算完成。

7. **版本化与评测**
   每次修改提示词都要：
   - 更新 `PROMPT_VERSION`；
   - 运行 `npm test` 与 `npm run evals`；
   - 有真实模型环境时运行 `npm run evals:live`，记录模型、样本和限制；
   - 更新 `CHANGELOG.md`。
   不要把某一个模型的偶然偏好固化成通用规则；提示词应服务目标，而不是服务某次输出。

## 当前结构

```text
src/core/prompt.ts      PROMPT_VERSION、短核心提示词、modelInput() 上下文裁剪
src/core/intent.ts      当前任务的轻量判断与任务级提示
src/core/strategy.ts    软件任务的方案边界
src/core/defaults.ts    页面类默认项
src/guards/             结果与来源的确定性检查
src/core/engine.ts      模型调用、修复和总长度/时间预算
```

当前基线（会随版本变化）：

| 指标 | 值 |
| --- | --- |
| 核心提示词 | 约 1,500 个 Unicode 字符 |
| 写作任务输入 | 约 330 个字符 |
| 带默认项的页面任务输入 | 约 880 个字符 |

## 修改流程

1. 先判断规则属于哪一层：所有任务都适用才进核心，任务相关放进 `intent` / `strategy` / `defaults`。
2. 不要在核心提示词里重复任务模块已有的内容。
3. 能用确定性代码检查的内容，优先写进 `guards/` 和测试，而不是继续加提示词。
4. 修改后运行 `npm run verify`，并检查 `tests/prompt.test.ts` 的渐进上下文断言。
5. 如果改变输出契约或默认项，补对应守卫测试；不要只改提示词。
6. 在 `CHANGELOG.md` 记录用户能感知的变化和未验证的边界。

## 评测边界

离线测试验证的是字段裁剪、契约和守卫，不证明真实模型输出质量。日常修改至少要跑通 83 条构造样例和 18 组质量对照的 36 项正反断言；真实模型效果仍需人工盲评或真实模型实测，并在发布说明里保留样本量和限制。

0.2.5 的有限同义词族与显式并列任务检查放在 guards/task.ts，不扩大核心提示词。不把任意语义关系硬编码成等价；带引号的代码、数字、路径和禁止项继续独立严格检查。新增样例必须同时验证正常改写可接受、遗漏任务会回退，并说明样例是人工编写还是来源于经允许的真实反馈。

0.2.6 的 PROMPT_VERSION 为 4：core/clauses.ts 从明确动作中提取并列、编号和顺序步骤，供 task_intent 与守卫共用；带代码引用不再令其他任务的检查整体失效。它仍是有界词法规则，不保证任意长句或隐含任务的完整解析。

选中文件由 core/excerpts.ts 提取相关原文与行号来源，保留少量开头；没有相关匹配时使用开头。只处理用户已经选择、且通过原有安全与大小检查的文件，不扫描目录、不做额外模型调用。

reference_fragments 仅包含客户端提供的引用显示文字，不包含运行时引用身份或引用展开内容；模型按需收到保留引用的指引。客户端最终检查引用身份和原子坐标，跨引用的结果不会回填。引用草稿不追加页面默认模板，避免跨越原子节点。原生 mode 设置仅覆盖显式请求 use_configured_mode 的客户端，其他接口仍遵守请求自己的 mode。

0.2.8 的 PROMPT_VERSION 为 5。task-defaults.ts 只为明确任务提供交付组织方式；动态网站默认工具不冒充项目事实，服务端与存储仍取决于实际数据需求。default-coverage.ts 只识别自有固定默认项的关键内容，阻止重复追加，不授权额外实体或数字。wording.ts 的偏好替代表达仅限明确词组；逐字禁止项仍优先。

历史按新到旧排列并优先分配剩余预算，只有明确换题才切断旧历史；context_guidance 仅在有资料时发送。refinement.ts 识别默认段落或至少三个任务字段，只用于限制扩写，不断言语义已完整。再次点击当前采纳稿使用 light，用户编辑后恢复配置模式；不需要新增请求字段或额外分类模型。
