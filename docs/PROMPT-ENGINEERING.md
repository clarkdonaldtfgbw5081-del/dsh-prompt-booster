# 提示词工程说明

这页说明本插件如何组织系统提示词、任务上下文和输出契约。它不是给模型的另一个提示词，而是维护提示词时的设计约束。

## 原则

1. **最小核心**
   系统提示词只保留所有任务都需要的部分：改写者身份、输入边界、原意保护、输出结构和完成定义。页面方案、排错步骤、写作语气等任务知识不写进核心提示词。

2. **按需展开**
   `modelInput()` 只发送当前任务会用到的字段：
   - 写作、研究、分析通常只带 `task_intent` 和长度预算；
   - 软件任务才带 `solution_strategy`；
   - 页面默认项只在 `default_choices` 非空时发送；
   - 没有逐字保护片段时不发送 `protected_fragments`；
   - `context_sources`、`preferences` 为空时不占模型上下文。

3. **任务指导就近**
   任务相关的指引放在产生它的模块里，而不是全部塞进 `SYSTEM_PROMPT`：
   - `intent.ts`：任务类型、交付阶段、已有项目等轻量判断；
   - `strategy.ts`：软件任务的方案边界与按能力选择的验证方向；
   - `defaults.ts`：可调整的页面默认项；
   - `guards/`：确定性约束检查；
   - `engine.ts`：修复请求和总预算。

4. **少写菜谱，多写目标和边界**
   当前模型对任务意图的理解已经足够强，过细的逐条步骤会压缩用户的真实要求，也容易让模型只记住模板。核心提示词使用正面目标（“保留原意、说明交付、遵守预算”），只有安全边界、输出契约和用户可见行为才写成硬规则。

5. **提示词不是安全边界**
   不执行任务、不自动发送、不增加用户没有要求的功能，这些由产品结构和本地守卫保证；提示词负责表达意图，`guards/` 负责兜底。修改提示词时不要假设模型一定会遵守所有文字，新增约束优先加到守卫和测试。

6. **先定义完成**
   完成定义写在核心提示词末尾：JSON 可解析、原要求与逐字约束完整、默认项不过界、正文在预算内。模型不需要输出自评，但需要知道什么算完成。

7. **版本化与评测**
   每次修改提示词都要：
   - 更新 `PROMPT_VERSION`；
   - 运行 `npm test` 与 `npm run evals`；
   - 有真实模型环境时运行 `npm run evals:live`，记录模型、样本和限制；
   - 更新 `CHANGELOG.md`。
   不要把某一个模型的偶然偏好固化成通用规则；提示词应服务目标，而不是服务某次输出。

## 当前结构

```text
src/core/prompt.ts      PROMPT_VERSION、短核心提示词、modelInput() 上下文裁剪
src/core/intent.ts      当前任务的轻量判断与任务级提示
src/core/strategy.ts    软件任务的方案边界
src/core/defaults.ts    页面类默认项
src/guards/             结果与来源的确定性检查
src/core/engine.ts      模型调用、修复和总长度/时间预算
```

当前基线（会随版本变化）：

| 指标 | 值 |
| --- | --- |
| 核心提示词 | 约 1,500 个 Unicode 字符 |
| 写作任务输入 | 约 330 个字符 |
| 带默认项的页面任务输入 | 约 880 个字符 |

## 修改流程

1. 先判断规则属于哪一层：所有任务都适用才进核心，任务相关放进 `intent` / `strategy` / `defaults`。
2. 不要在核心提示词里重复任务模块已有的内容。
3. 能用确定性代码检查的内容，优先写进 `guards/` 和测试，而不是继续加提示词。
4. 修改后运行 `npm run verify`，并检查 `tests/prompt.test.ts` 的渐进上下文断言。
5. 如果改变输出契约或默认项，补对应守卫测试；不要只改提示词。
6. 在 `CHANGELOG.md` 记录用户能感知的变化和未验证的边界。

## 评测边界

离线测试验证的是字段裁剪、契约和守卫，不证明真实模型输出质量。日常修改至少要跑通 80 条构造样例；真实模型效果仍需人工盲评或 `evals:live`，并在发布说明里保留样本量和限制。
