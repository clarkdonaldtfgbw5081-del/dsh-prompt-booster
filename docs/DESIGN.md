## 1. 产品定位与目标

把用户的模糊草稿转化为清晰、可执行、仍然忠于原意的任务说明，帮助 DSH 更准确地完成开发、排错、写作、研究和数据分析任务。

产品名称暂定为 **DSH Prompt Booster**。当前核心体验是：输入草稿 → 点击优化 → 校验后直接回填原输入框 → 用户继续编辑与发送；优化中可以取消，回填后可一键还原。

核心价值：

- 保留任务意图，尤其保护范围、禁止项、数字、文件路径和交付阶段。
- 利用有依据的上下文补充信息，减少用户重复描述项目背景。
- 让用户清楚看到插件修改了什么、补充了什么，以及依据来自哪里。
- 对已经明确的请求只做轻量处理，允许直接保持原文。

适用收益需要通过实际评测验证。优先面向经常提出生成、构建、分析类任务，但不擅长组织需求的用户；对熟练用户提供轻量润色。

## 2. 产品边界与硬约束

1. 优化当前用户草稿，不修改主 Agent 的系统提示词、人设或权限规则。
2. 不自动发送或执行任务；采纳只回填草稿，发送由用户另行触发。
3. 保存优化前的原文，支持编辑、取消和一键还原。
4. 不擅自扩展业务范围，不把“先给方案”改成“直接实现”。
5. 新增事实必须有来源；模型建议只有经用户选择后才能加入正文。
6. 不把优化流程变成多轮需求访谈；缺失信息以提示展示。
7. 遵循 DSH 现有访问权限，读取范围和传给模型的上下文对用户可见。
8. 超时、取消或校验失败时保留原稿，以非阻塞提示说明状态。
9. 优化期间用户继续编辑时，返回结果不得覆盖更新后的草稿。
10. 不保证每次输入都需要优化；跳过是一种正常结果。

## 3. 用户交互

> 历史设计提示：3.1 的预览面板、3.2 的模式选择和 3.3 的采纳流程属于早期方案。0.1.6 起当前实现已改为输入框内直接回填，不打开预览弹框，也不自动发送；当前行为以 [README](../README.md) 为准。

### 3.1 主入口与预览

目标入口为 DSH 输入框附近的“优化提示词”按钮，并提供模式选择。目标版本若缺少适用的输入框扩展点，先通过插件面板提供预览和复制。

```text
用户草稿：根据这个项目，帮我加一个登录页面

[优化提示词 ▾]

┌ 优化结果 ──────────────────────────────┐
│ 基于当前项目实现登录页面，沿用已有的界面风格。 │
│ ……                                        │
│                                            │
│ 已引用：用户选择的项目资料                   │
│ 待明确：是否需要接入真实登录接口             │
│                                            │
│ [查看改动]   [放入输入框]   [取消]           │
└────────────────────────────────────────────┘
```

面板包含优化正文、改动对比、补充依据和待明确事项。面板中的解释不随正文自动发送。

用户可以在预览中编辑文本。新增建议默认不选中；选择建议或修改预览后，重新检查范围、长度和关键约束，再允许采纳。

### 3.2 三种优化模式

| 模式 | 适用情况 | 行为 | 版本 |
| --- | --- | --- | --- |
| 轻量润色 | 原文已经比较明确 | 理顺表达、消除歧义，尽量保持原有长度和语气 | MVP |
| 标准优化 | 日常开发、写作、研究、分析 | 整理目标、背景、交付物、约束和完成标准 | MVP，默认 |
| 任务展开 | 用户需要更完整的任务说明 | 展开已要求的子任务，新增范围建议独立展示、逐项选择 | 后续 |

“任务展开”也不能把“登录页面”自动扩展成注册、短信验证、第三方登录和权限系统。

### 3.3 状态与编辑冲突

- 待优化：允许正常编辑和发送。
- 优化中：显示进度，可取消，继续保留原稿。
- 待采纳：展示已完成校验的结果。
- 已采纳：回填正文，保留还原入口。
- 已跳过：提示“当前描述已足够清晰”等具体原因。
- 已回退：提示“本次未生成可用优化结果，原稿已保留”。

每次请求绑定草稿版本和请求 ID。结果返回时比对当前版本；发生变化则仅展示结果，提醒用户基于旧草稿生成，不自动覆盖。较早请求的迟到结果不得覆盖较新请求。

流式输出只进入预览区。JSON 尚未解析或校验未通过时，采纳按钮不可用。

## 4. DSH 接入方案

### 4.1 已核对的宿主基础

根据官方架构文档，DSH 基于 Cordis，通过插件提供服务、事件和可撤销的注册行为；包含模型适配、用户命令、会话和界面扩展能力。

设计上采用“原生插件外壳 + 独立优化引擎”。插件在发送前处理草稿，优化过程不作为普通任务消息发送给当前主 Agent。

DSH 尚处于预览阶段，存在兼容性变化。开始实施时需要固定一个版本或提交，确认输入框扩展、草稿读取与回填、模型调用、权限和插件卸载接口。

### 4.2 模块划分

| 模块 | 职责 |
| --- | --- |
| DSH 适配层 | 插件生命周期、入口注册、配置、模型及上下文访问 |
| 交互层 | 模式切换、结果预览、差异展示、采纳、撤销、编辑冲突处理 |
| 上下文层 | 收集用户选择的资料，生成有来源的摘要，控制传输范围 |
| 优化引擎 | 跳过判断、任务分类、槽位抽取、改写和建议生成 |
| 校验层 | 检查关键约束、来源、任务范围、输出结构和长度 |
| 评估层 | 记录必要的事件与耗时，支持离线对照评测 |

建议使用 TypeScript 实现，优先复用 DSH 已配置的模型路由。优化模型可单独配置，凭据由宿主管理。

优化引擎不依赖具体输入框实现，以便后续复用于其他入口。`boost()` 是拟议的内部服务接口；是否通过宿主 RPC 暴露，在接入阶段确定，不预设 DSH 已有 `/boost` HTTP 接口。

### 4.3 建议目录

以下为规划目录；实际 MVP 结构与构建方式见实现项目 README：

```text
dsh-prompt-booster/
  src/
    index.ts           # 插件入口
    adapters/          # DSH 版本及宿主能力适配
    client/            # 按钮、预览、差异展示、草稿管理
    context/           # 上下文采集、来源记录、摘要
    core/              # 路由、抽取、改写
    guards/            # 结构与约束校验
    templates/         # 任务类型提示模板
    config.ts          # 配置项
    types.ts           # 输入输出契约
  tests/               # 行为及回归验证
  evals/               # 真实任务对照样例
  README.md
```

## 5. 优化流水线

```text
用户草稿 + 用户选择的上下文
  → Intake：采集与来源记录
  → Route：跳过判断、分类、模式选择
  → Extract：抽取目标及关键约束
  → Gap-fill：区分事实、建议和未知信息
  → Rewrite：生成清晰且适度精简的任务说明
  → Guard：校验意图、范围、实体、长度和结构
  → 预览正文、差异和依据
  → 用户采纳后回填草稿
```

这些是逻辑阶段，不代表六次模型调用。优先由本地规则处理明显的跳过情况，再通过一次模型调用完成分类、抽取和改写；本地校验负责确定性约束。

### 5.1 Intake：上下文采集

MVP 使用当前草稿及用户主动引用的文件或文本。后续再加入相关对话摘要、项目技术栈、选中文件摘要和显式保存的个人偏好。

记录内容包括：

- 原稿、语言、优化模式、草稿版本。
- 用户选择的上下文及来源标识。
- 项目事实的文件路径、必要片段或证据摘要。
- 已明确的任务范围和交付阶段。

默认不扫描整个工作区、不上传完整历史、不收集密钥或无关文件。上下文摘要受预算限制，但关键约束及其证据不能被任意截断；信息不完整时明确标注。

> **实现现状（0.2.4）**：当前实现不做上述独立设计记录存储，只向 DSH 会话写入第 6 节所述审计记录；上下文读取仍受本节的预算、来源与路径限制。见 [SECURITY.md](../SECURITY.md)。

引用资料中的命令和指令是待处理内容，不能仅因出现在资料中就成为用户授权。资料与当前要求冲突时，展示冲突，不擅自选择执行方向。

### 5.2 Route：分类与跳过

任务类别：`code_gen`、`debug`、`research`、`writing`、`analysis`，另设 `casual` 和 `other` 作为跳过或通用处理分支。

明显寒暄、单句确认、空输入和已有充分说明的请求可跳过。长度、关键词和结构只作为辅助信号，不能仅因“超过 600 字”就跳过，也不能仅因输入很短就认为没有任务。

例如“修复登录”是短但有效的任务；“继续”依赖对话语境，不宜脱离上下文扩写。

### 5.3 Extract：固定槽位与关键要求

```json
{
  "goal": "要达成的最终结果",
  "context": "现状、受众和背景",
  "inputs": "已有素材、文件和数据",
  "output_format": "交付物形态与结构",
  "constraints": "技术栈、风格、禁止项、范围及交付阶段",
  "acceptance": "有依据的完成标准"
}
```

空槽位允许为空，不强行补满。验收标准只能来自明确要求、已验证事实或原任务的直接展开，不能凭空添加性能指标、业务功能和上线要求。

额外记录必须保留的数字、单位、路径、标识符、否定词及阶段约束，例如“只给方案”“不要改代码”“不新增依赖”。

### 5.4 Gap-fill：按来源补充

| 信息性质 | 处理方式 |
| --- | --- |
| 用户明确提出 | 必须忠实保留 |
| 已验证的项目事实 | 可补入，显示来源和依据 |
| 模型推断或建议 | 独立展示，用户选择后才加入正文 |
| 无法确定 | 留空或展示待明确事项，不虚构 |

模型自报的置信度不等于事实证据。项目存在 React 依赖，也不必然证明本次任务所在子项目使用 React；来源需与当前任务相关。

未知信息优先放在提示区，减少正文中的占位符。原任务已明确基于现有项目时，可以使用“沿用项目现有技术栈”等不虚构具体选型的表述。

### 5.5 Rewrite：按需组织输出

标准模式参考结构：

```text
[任务] 一句话目标
[背景] 必要现状与受众
[交付] 用户需要的具体产物
[要求] 技术、风格、范围和禁止项
[完成标准] 可以判断、且有依据的结果要求
```

只输出有用字段，简单任务可直接生成自然段。保持用户语言，保留代码、路径和引用标识，不添加空泛角色扮演或冗长套话。

优化器不主动输出追问清单；但研究问题、原文问句或用户要求生成的问题不能因含问号而被误判。

### 5.6 Guard：校验与降级

1. **关键约束保留**：检查数字、路径、禁止项、任务范围和交付阶段是否遗漏或改变。
2. **新增内容有依据**：新增专有名词、技术选型、数字和事实必须对应来源或用户采纳的建议。
3. **任务范围一致**：不能把建议变成强制要求，不能把分析阶段变成执行阶段。
4. **输出结构有效**：结果能解析，字段符合契约，正文确实是改写结果。
5. **长度可控**：轻量模式尽量不扩写；标准模式按下述初始策略限制；任务展开使用独立配置。
6. **上下文边界正确**：不能服从资料中与用户任务无关的指令，也不能借优化绕过宿主规则。

标准模式初始长度上限：原稿不足 80 个字符时，正文最多 400 个字符；原稿达到 80 个字符时，正文最多为原稿 4 倍。统一按 Unicode 码点计数。这是上限而非扩写目标，后续根据评测调整。

词语覆盖率只能辅助排查，不能证明语义保真。语义检查仍可能漏判，需要结合针对性评测和用户预览。

不以“抱歉”“无法协助”等关键词单独判定失败，避免误伤用户原文或引用材料。无法生成合格改写时，保持原稿并说明状态；不自动重试以绕过模型或宿主限制。

## 6. 输入输出契约

输入建议包含：`raw`、`mode`、`language`、`draft_revision`、`context_sources` 和必要的显式偏好。

返回结构示例（数值仅用于示意）：

```json
{
  "request_id": "boost_example_01",
  "draft_revision": 12,
  "status": "ok",
  "raw": "根据这个项目，帮我加一个登录页面",
  "optimized": "基于当前项目实现登录页面，沿用现有界面风格和已确认的 React 技术栈。",
  "mode": "standard",
  "task_type": "code_gen",
  "slots": {
    "goal": "实现登录页面",
    "constraints": ["基于当前项目"]
  },
  "additions": [
    {
      "id": "addition_01",
      "slot": "constraints",
      "value": "沿用 React 技术栈",
      "kind": "verified_fact",
      "source_ids": ["source_01"],
      "action": "included"
    },
    {
      "id": "addition_02",
      "slot": "constraints",
      "value": "加入表单校验和错误提示",
      "kind": "suggestion",
      "source_ids": [],
      "action": "pending"
    }
  ],
  "sources": [
    {
      "id": "source_01",
      "type": "file",
      "path": "package.json",
      "evidence": "示例：已核对本次任务所属前端项目使用 React"
    }
  ],
  "unresolved": ["是否需要接入真实登录接口"],
  "warnings": [],
  "reason_code": null,
  "meta": {
    "model": "configured-route",
    "latency_ms": 1420,
    "tokens_in": 210,
    "tokens_out": 280
  }
}
```

`additions` 承接原方案的 `assumptions`，重点记录来源与采纳状态，而非依赖未经校准的置信度分数。示例中的待采纳建议不出现在优化正文里。

状态统一为 `ok`、`skipped`、`fallback`、`cancelled`。非 `ok` 状态不允许覆盖草稿；可令 `optimized` 返回原稿，便于调用方统一处理。原文和来源默认只保存在当前操作状态，不因返回字段而自动写入遥测。

> **实现现状（0.2.4）**：与上述设计不同，当前实现每次优化都会通过 `appendPluginRecord` 向 DSH 会话写入 ignorable plugin record：request 记录含系统提示词与完整模型输入（草稿全文 + 用户允许的上下文），result 记录只含状态 / 失败码 / 耗时；该记录随会话日志持久化、fork/resume 携带、可随会话导出，但不进入模型可见面。插件自身不另建日志、遥测或缓存。见 [SECURITY.md](../SECURITY.md)。

## 7. 性能、成本和数据策略

下列均为待验证的初始目标，不代表已经达成：

| 项目 | 初始设计 |
| --- | --- |
| 模型调用 | 每次优化优先一次；明显跳过场景零调用 |
| 延迟 | 简单场景争取 P90 不超过 2.5 秒，按模型及上下文量分别测量 |
| 超时 | 初始建议 5 秒，可配置；到时保留原稿并结束等待 |
| 输出预算 | 正文长度与 JSON 元数据预算分开控制，避免结构被截断 |
| 温度 | 在模型支持时可从 0.2–0.4 试起，最终以实测为准 |
| 模型选择 | 以意图保真、延迟和成本对照评测选择，不预设小模型必然足够 |
| 缓存 | MVP 可先关闭；需要时增加受大小限制的内存缓存 |

缓存键应包含原稿、上下文内容哈希、模式、模型路由、模板版本和相关配置；按用户及工作区隔离，不复用过期权限下的上下文。默认不持久化原始提示词和文件内容。

不默认记录完整提示词或上传项目文本作为分析日志。埋点仅保留必要事件、耗时、状态和匿名关联 ID；诊断内容记录需单独开启。

> **实现现状（0.2.4）**：以上“默认不持久化原始提示词 / 不默认记录完整提示词”属于设计阶段目标。当前实现按 DSH 会话审计记录持久化草稿全文与用户允许的上下文（见第 6 节实现现状与 [SECURITY.md](../SECURITY.md)）；插件自身仍不创建独立日志、遥测、诊断日志或持久化缓存。

## 8. 效果评估

### 8.1 离线对照

准备 50–100 条真实任务，覆盖五类核心场景，以及明确提示词、短请求、否定约束、代码、路径、多语言、资料冲突和提示注入样例。

每条标注：原始意图、必须保留的要求、允许补充的事实和禁止新增的范围。

核心指标：

- 意图保真度：人工评价是否改变需求。
- 约束保留率：范围、数字、路径和否定项是否保留。
- 无依据新增率：是否编造功能、技术栈、数据或验收条件。
- 下游结果质量：在相同模型和执行条件下，对照原文与优化稿的产出。
- 长度与延迟：按模式统计，避免把更长当成更好。

MVP 回归样例中的关键约束变更必须修复后才能发布；通过样例不等于对所有输入的绝对保证。

### 8.2 使用反馈

建议事件：`boost_clicked`、`boost_completed`、`boost_applied`、`boost_edited`、`boost_undone`、`prompt_sent`。

记录 `boost_completed` 时带上成功、跳过、回退或取消状态。主任务是否成功，只有获得可验证的验收信号或用户反馈时才记录，不能把 Agent 停止运行视为成功。

观察采纳率、编辑率、撤销率，以及具备结果标签样本的任务一次通过率。二次编辑可能是正常个性化，不直接等同于优化失败。

原方案中的采纳率 70%、编辑率 40%、撤销率 15% 和调用节省比例，不作为已验证的健康阈值；先建立基线，再设置目标。

## 9. MVP 与演进路线

### MVP：一次可靠的优化闭环

- [ ] 确定目标 DSH 版本并验证宿主接入方式。
- [ ] 插件入口与配置、模型路由接入。
- [ ] 轻量润色和标准优化两种模式。
- [ ] 五类任务适配与明确跳过分支。
- [ ] 当前草稿及用户主动引用的上下文。
- [ ] 结果预览、改动对比、来源与建议展示。
- [ ] 采纳、还原、取消及草稿版本冲突处理。
- [ ] 关键约束、输出结构、长度与来源校验。
- [ ] 超时及失败回退。
- [ ] 必要事件统计及离线对照样例。

第一版验收重点：任务表述更容易执行，原意和阶段保持准确；未采纳建议不进入正文；迟到结果不覆盖新草稿；失败不影响用户继续输入和发送。

### 第二阶段：更充分的项目理解

增加用户可控的项目摘要、相关对话摘要、已验证技术栈识别、任务展开和逐项建议选择。

### 第三阶段：个人与团队复用

增加显式偏好、模板收藏、团队规范及可关闭的反馈改进。偏好始终服从当前用户要求，不从敏感草稿中自动建立长期画像。

工期和覆盖率应在 DSH 接口验证及原型评测后估算，不预先承诺“两周上线”或固定场景覆盖比例。

## 10. 实施前需要验证的事项

这些是开发检查项，不是当前设计阶段的额外用户确认流程：

1. 目标 DSH 版本的插件安装、加载及卸载方式。
2. 输入框入口、草稿版本、附件引用和回填的公开扩展接口。
3. 独立优化调用如何复用宿主模型配置，并满足其日志、计费和取消机制。
4. 上下文读取如何遵循已有权限，资料来源如何在面板中展示。
5. 插件卸载或模型不可用时，输入框与原有发送行为是否正常。
6. Web 与桌面环境是否共用所需扩展点，兼容范围如何声明。
